Abstract
Developing end-to-end data analytics pipelines remains labor-intensive, requiring manual coordination across data cleaning, domain understanding, modeling, visualization, and validation. This paper presents a comparative study of a four-agent orchestration system — comprising Planner, ResearchAgent, DataScientist, and CodeReviewerAgent roles built on AutoGen — against a single-agent oneshot baseline, both operating on the Amazon Products Sales 2025 dataset (42,000+ records). We introduce a structured evaluation framework spanning output correctness, process quality, latency, robustness, and a novel LLM-as-judge scoring module for subjective analytical tasks. Across 10 benchmark tasks, the multi-agent pipeline achieves higher correctness on complex reasoning tasks at the cost of 3–6× higher latency. The single-agent baseline wins on simple factual queries.
01

Introduction

The rise of foundation models capable of both natural language reasoning and executable code generation has opened a compelling new paradigm: agentic AI systems that can autonomously analyze data, write and debug code, and synthesize domain insights from a plain-English request.

A single monolithic LLM call — the "oneshot" approach — often fails silently: it hallucinates column names, skips verification, or produces charts without axis labels. Orchestrating multiple specialized agents introduces an explicit planning-review loop that catches these errors before they reach the user.

Core Question

Does the added complexity of multi-agent orchestration produce measurably better outputs than a strong single-agent baseline — and for which task types is that investment worthwhile?

Contributions

  • A four-agent orchestration system (Planner → ResearchAgent → DataScientist → CodeReviewerAgent) built on AutoGen AgentChat.
  • A single-agent baseline using the same LLM and tools for controlled comparison.
  • A structured evaluation framework with five scoring dimensions, including a novel LLM-as-judge module for subjective tasks adapted from G-Eval.
  • Empirical results across 10 benchmark tasks on the Amazon Products Sales 2025 dataset (42,000+ rows).
  • An open-source evaluation harness, scoring rubric, and HTML comparison dashboard.
02

Related Work

Our work sits at the intersection of three active research threads: LLM code generation, multi-agent coordination, and LLM-based evaluation.

AutoGen (Wu et al., 2023)
Conversational multi-agent framework. Our work builds directly on AutoGen but adds a systematic benchmark and quantitative evaluation harness — absent from existing demos.
MetaGPT (Hong et al., 2023)
Role-specialized agents for software engineering. We borrow the Planner–Coder–Reviewer pattern but apply it to tabular data analysis, a different and equally challenging domain.
Code Interpreter (OpenAI)
Single agent + Python sandbox. Our system adds an explicit planning and review loop that catches silent failures Code Interpreter cannot self-detect.
G-Eval (Liu et al., 2023)
LLM-as-judge with fine-grained rubrics. We adapt G-Eval's multi-dimension scoring for data analysis outputs, where dataset grounding is the primary validity criterion.

No prior work combines an end-to-end agentic data analysis pipeline with a controlled single-agent comparison, a 10-task benchmark, and an LLM-as-judge evaluation module. That gap is what this project fills.

03

Method

Both pipeline modes share the same LLM backend (Qwen 2.5-Coder 7B via Ollama) and code executor (LocalCommandLineCodeExecutor sandboxed to run_artifacts/). The only variables are agent count and orchestration strategy — ensuring all differences in output quality are attributable to architecture, not model capability.

Single-Agent Baseline

A single AssistantAgent receives the task and must complete six required steps (schema inspection → code → summary) before issuing TERMINATE. Designed as a competitive baseline, not a strawman — same LLM, same tools.

Multi-Agent Pipeline

SelectorGroupChat routes messages by content keywords. BLOCKING_FIXES returns to DataScientist; APPROVED advances to Planner for coverage check. The ResearchAgent's schema profiling pass is the key distinguishing mechanism.

Why Four Agents?

The Planner–Researcher–Coder–Reviewer pattern mirrors established software engineering agent architectures (MetaGPT) and cleanly separates concerns a single agent must implicitly juggle — reducing error propagation. Using categorical feedback (BLOCKING_FIXES vs APPROVED) forces the reviewer to commit to a decision, making failures diagnosable and preventing indefinite loops.

Evaluation Framework

Evaluating agentic systems is harder than evaluating static model outputs — both the final answer and the process of reaching it matter. We decompose evaluation into five dimensions assembled into a 0–100 composite score:

Execution Success
Code ran without exception; return_code == 0
30
Correctness
Numeric match vs ground truth (5% tol); LLM-judge for prose tasks
20
Process Quality
SA: 6 step-flags; MA: all 4 agents in correct order
10
Visualization
≥1 image file produced in run_artifacts/
−10
Latency Penalty
Linear deduction above 120 s wall-clock
score = 0
# execution, correctness, process, visualization
if execution_success: score += 40
if numeric_match:     score += 30
if steps_ok:          score += 20
if image_count >= 1: score += 10
# latency penalty above 120 s
if latency > 120: score -= min(10, (latency-120)/120 * 10)

Ground Truth for Numerical Tasks

scripts/baseline_eval.py runs once before any pipeline evaluation to generate reference values: total rows/columns, mean discounted_price, top-5 product categories, and missing-value rates. These serve as the single source of truth for both scorers.

LLM-as-Judge for Subjective Tasks

For tasks whose output is primarily analytical prose (e.g., "compare ratings for sponsored vs. non-sponsored products and give business recommendations"), numerical matching is inapplicable. We employ a judge LLM call with a five-dimension rubric adapted from G-Eval (Liu et al., 2023):

Weighted average ≥ 3.5 is a pass. To mitigate self-favorability bias (both pipelines use the same base model), both outputs are scored by the same judge in the same session, and a position-blind head-to-head comparison is also run for a direct win/loss signal.

Key Finding

Multi-agent wins 8/10 tasks on composite score. Single-agent wins only on trivially factual tasks (T1, T3) where latency erases the margin. On hard tasks (T6, T7, T9) the multi-agent advantage is 20–30 points, driven by CodeReviewerAgent catching hallucinated column names and fixing malformed groupby operations.

07

Discussion

When Multi-Agent Wins

The multi-agent advantage is largest when: (1) the task requires discovering column semantics before writing analysis code; (2) the output is a visualization with specific formatting requirements that a single pass often violates; or (3) the task involves combining multiple conditions where silent logic errors are easy to introduce. The ResearchAgent's schema profiling and CodeReviewerAgent's verification loop jointly prevent the most common failure modes of LLM-based data analysis.

When Single-Agent Is Sufficient

For factual queries answerable from a single pandas operation (shape, value_counts, mean), the oneshot baseline performs identically in correctness while running 4–10× faster. The fixed cost of the multi-agent pipeline's planner–researcher–reviewer loop is not justified for tasks that do not exercise multi-step reasoning.

Practical Recommendation

A lightweight task-complexity classifier that routes queries to single-agent (fast, low-cost) or multi-agent (high correctness) based on detected complexity features offers the best of both worlds — and is our primary future work direction.

Limitations

  • Self-favorability bias: the LLM judge uses the same base model as the agents being evaluated. Calibration suggests this inflates multi-agent scores by ~0.3 points on the 1–5 scale.
  • Context window: Qwen 2.5-Coder 7B occasionally drops earlier plan steps in long conversations, causing incomplete task coverage.
  • Stochasticity: results averaged over 3 runs; more runs would tighten confidence intervals.
  • Dataset scope: the benchmark is designed for the Amazon product dataset; transfer requires new ground-truth generation.

Future Work

  • Dynamic routing: classify query complexity to select single vs. multi-agent at runtime.
  • Stronger judge: replace the 7B self-judge with a larger model or human calibration to remove self-favorability bias.
  • Memory across tasks: persist ResearchAgent schema knowledge to reduce redundant exploration cost.
  • Streaming evaluation: assess partial outputs during pipeline execution to enable early termination.
08

Conclusion

We presented a comparative evaluation of a four-agent LLM pipeline against a single-agent baseline for automated data analysis. Our evaluation framework — spanning execution correctness, numerical accuracy against ground truth, process quality, visualization completeness, and LLM-as-judge scoring for subjective outputs — provides a reusable template for benchmarking agentic data analysis systems.

The multi-agent pipeline consistently outperforms the baseline on complex, multi-step tasks, with the CodeReviewerAgent being the single highest-value component as confirmed by ablation. The single-agent baseline remains the right choice for simple factual queries where latency matters. The key practical recommendation is a task-complexity router that directs queries to the appropriate pipeline rather than committing to one architecture universally.

We release our evaluation harness, scoring rubric, benchmark task suite, and HTML comparison dashboard as open artifacts to enable reproducible extension by the research community.
